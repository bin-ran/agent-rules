# Git 提交流程规则

适用前提：以下工序均以「提交尚未推送到远端」为前提；已推送的历史一律不改写（该禁令常驻在 AGENTS.md 的「Git 提交规则」中）。

- 按不同工作项拆分提交，使用 conventional commits 风格的类型前缀，不把不同性质的工作混在一个提交里：
  - `feat` 新功能
  - `fix` 修复 bug
  - `docs` 文档
  - `style` 格式（不影响代码运行的变动）
  - `refactor` 重构（既不是新增功能，也不是修改 bug 的代码变动）
  - `test` 增加测试
  - `chore` 构建过程或辅助工具的变动
  - `revert` 撤销之前的 commit（如 `revert: feat(pencil): add 'graphiteWidth' option`）
  - 格式：`类型: 简要描述`；需要标明范围时可加 scope，如 `feat(ssh): ...`。
- **每个提交都必须独立可用**：切到任意一个提交节点，项目都能构建通过、静态检查和测试全部通过，不能只保证最终状态可用。
- 某个提交中引用的函数/类型/配置项等定义，必须在该提交内或更早的提交中已存在；尤其注意测试文件不能引用后续提交才加入的定义（常见坑：测试随实现分批提交时顺序放错）。
- 测试文件要么与对应功能的实现在同一提交，要么放在所有相关功能之后单独提交。
- 提交前先查看 `git status` / `diff` 确认改动范围，只暂存与本次工作相关的文件；不盲信 .gitignore，防止临时文件、构建产物、本地配置混入提交。
- 提交说明语言与仓库现有历史保持一致；仓库没有历史时默认使用中文。
- 拆分提交后需逐节点 checkout 验证构建与测试；若验证发现历史不可用，先向用户说明问题及建议（如合并为单个提交），经确认后再回退重做，并对比新旧树确保零丢失。
- 提交前先和用户确认要细粒度历史还是单个合并提交，不确定时宁可问一句，避免自作主张反复重写历史。
